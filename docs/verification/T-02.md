## 3. Befunde

### F-02 · Medium · `client_submission_id` ist global eindeutig statt je Patientin
- **Anforderung:** Vertrag §2 „Fremdes Objekt ⇒ 404“, `openapi.yaml` `POST /me/responses` idempotent über `client_submission_id` (v1.1 G-10: gleiche ID + anderer Body ⇒ 409). Idempotenz ist ein Schlüssel **je Patientin**.
- **Commit:** `084f41f`, `models.py` `Response.client_submission_id unique=True`, `migrations/w001` (gleiches für `Assessment.client_submission_id`).
- **Schritte:** Test `test_a3_idempotency_key_is_scoped_per_patient` (legt für SYN-0001 und SYN-0002 dieselbe ID an).
- **Erwartet:** beide Zeilen speicherbar (Eindeutigkeit `(patient_id, client_submission_id)`). **Beobachtet:** zweite Zeile `IntegrityError: UNIQUE constraint failed: wa_responses.client_submission_id`.
- **Beleg:** `challenge/backend/test_a3_t02.py` (xfail strict; Mutationsprobe: Unique im Migrationsskript entfernt ⇒ Test kippt auf XPASS = rot ✔).
- **Wirkung:** (a) Patientin B kann mit der (erratenen/abgefangenen) UUID von A eine Kollision auslösen (Existenzorakel, Fehlerpfad 500/409 statt neutraler Behandlung); (b) setzt T-03 „bereits gespeichert ⇒ gleicher Beleg“ nur über die ID um, bekäme B den Beleg von A (**Datenleck**). Heute noch kein Endpunkt, aber die Weiche steht im Schema von T-02 und ist später nur per Migration änderbar.
- **Kleinste Korrektur:** neue Migration/Anpassung `w001`: `UniqueConstraint("patient_id", "client_submission_id")` statt `unique=True`; ebenso `wa_assessments` (dort Eindeutigkeit je Patientin); T-03 sucht die Idempotenz nur im eigenen Subjekt. Bis T-03 reicht A0-Hinweis + T-03-Kriterium „fremde ID ⇒ kein Fremdbeleg“.

### F-01 · Low · Laufzeitfehler im Inhalt ⇒ 500 statt kontrollierter 503
- **Anforderung:** Handoff ANN-T02-03 „Inhalt nicht ladbar: 503 content_unavailable“.
- **Schritte:** Backend läuft, `rules.yaml` wird beschädigt (`rules: [unclosed`), `GET /config` als `doctor` (Test `test_a3_runtime_invalid_content_is_a_controlled_error`).
- **Erwartet:** 503 `content_unavailable`. **Beobachtet:** 500 `internal_error`, Log `unhandled error … error=ContentError` (kein Inhaltsleck, kein Traceback in der Antwort).
- **Kleinste Korrektur:** in `services/config.get_bundle` `ContentError` abfangen und als `ApiError(503, "content_unavailable", …)` weitergeben (Mutation im Prüfbericht geprüft: Test kippt dann auf XPASS).

### F-03 · Low · Datenbank ohne Wächter-Migration ⇒ Login für alle Rollen 503
- Bestätigt Handoff-Risiko: `resolve_patient_id` fragt `wa_patients` bei jedem Login. DB nur mit Plattform-Migration + geladenem Plugin ⇒ `POST /auth/login` (auch `admin`) **503 `db_unavailable`** (kontrolliert). Entwicklerablauf (`dev.ps1`, `app.cli migrate`) migriert beides; Fehlerbild nur bei veralteter Dev-DB. **Korrektur (optional):** Resolver toleriert fehlende Tabelle (`None`) und loggt, oder Hinweis in `docs/ENVIRONMENT.md` („nach Plugin-Aktivierung `python -m app.cli migrate`“).
